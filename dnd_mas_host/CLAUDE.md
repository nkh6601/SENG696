## Project Overview

This is a Dungeons & Dragons 5E multi-agent system (MAS) powered by CrewAI. The system orchestrates multiple AI agents that work together to create an interactive D&D experience, including a Narrator, NPCs, and a Judge to manage gameplay mechanics.

**Campaign**: "Humantown: Rescue from the Town of Slimes" - information exist in the MongoDB

### System Goals
This text-based, AI-generated interactive story system aims to:
1. **Dynamic Story Generation**: Generate narratives based on user prompts and story progress
2. **Interactive Control**: Allow players to control main character actions
3. **Rule Adherence**: Ensure all actions and stories align with D&D 5E 2014 game rules
4. **Avoid Invalid Input Confusion**: Validate and clarify ambiguous/invalid user prompts
5. **Maintain Consistency**: Prevent inconsistencies in AI-generated content using RAG and structured data
6. **Proactive NPCs**: Enable reactive behaviors from NPCs, environment, and storyline events

The system replaces the traditional Game Master role (narrative/storytelling, rule adjudication, NPC management, world-building) with specialized AI agents.

## Architecture

### V2 Architecture: Message-Passing with Blackboard Pattern

The system now uses a FIPA-inspired message-passing architecture with centralized Blackboard pattern:

**Entry Point**: `python -m dnd_mas_host.interface` (launches InterfaceAgentV2)

**Core Components**:

1. **HostManager** ([manager/host_manager.py](src/dnd_mas_host/manager/host_manager.py)) - System Backbone
   - Owns unified message queue
   - Routes ALL messages to appropriate agents
   - Kicks off agent execution (NarratorFlow, JudgeFlow)
   - Manages NPC crews (REUSE existing, CREATE new, DELETE inactive)
   - Owns BlackboardManager instance

2. **BlackboardManager** ([state/blackboard_manager.py](src/dnd_mas_host/state/blackboard_manager.py))
   - Centralized HostState access
   - Read/write with configurable logging (`ENABLE_BLACKBOARD_LOGGING` in config.py)
   - Reset turn state between prompts
   - NPC crew lifecycle management

3. **HostState** ([state/host_state.py](src/dnd_mas_host/state/host_state.py)) - Nested Structure
   - `workflow`: WorkflowState (step tracking, error handling)
   - `game_context`: GameContext (campaign, characters, venues - immutable)
   - `current_turn`: TurnState (prompt, action, consequences, reactions)
   - `output`: OutputState (narratives, previous context)

4. **Message Types** ([interface/message_types.py](src/dnd_mas_host/interface/message_types.py))
   - Agent-to-agent: VALIDATE_PROMPT, CHECK_FEASIBILITY, EVALUATE_CONSEQUENCE, etc.
   - Interface messages: REQUEST_DIFFICULTY_CHECK, DISPLAY_NARRATIVE, VALIDATION_ERROR
   - Error handling: FLOW_ERROR

**Message Flow**:
```
User Prompt → Interface → VALIDATE_PROMPT → Narrator → CHECK_FEASIBILITY → Judge
                ↓                                              ↓
        VALIDATION_ERROR (if invalid)                REQUEST_DIFFICULTY_CHECK
                                                              ↓
                                                    User rolls d20
                                                              ↓
                                              EVALUATE_CONSEQUENCE → Judge
                                                              ↓
                                              EVALUATE_REACTIONS → NPC Processing
                                                              ↓
                                              GENERATE_NARRATIVE → Narrator
                                                              ↓
                                              DISPLAY_NARRATIVE → Interface
```

### Legacy Architecture: Flow-Based Orchestration

The original system uses CrewAI's Flow pattern defined in [src/dnd_mas_host/main.py](src/dnd_mas_host/main.py):

- `HostState` (Pydantic model): Centralized state management tracking workflow progress, user prompts, action difficulty, NPC reactions, and narrative output
- `HostFlow`: Flow orchestrator with `@start()`, `@listen()`, and `@router()` decorators managing agent coordination
- Entry points: `kickoff()`, `plot()`, `kickoff_async()`, `plot_async()`

### Agent Classes & Responsibilities
Four specialized components in [src/dnd_mas_host/crews/](src/dnd_mas_host/crews/):

1. **Interface Agent** (Python class with GUI integration)
   - Displays narratives generated by other agents
   - Shows necessary information: main character (Health, Skills, Items), NPC (Health)
   - Displays action difficulty (1-20 scale, higher = more difficult)
   - Performs difficulty checks via random roll (success if roll > difficulty)

2. **Narrator Flow** ([narrator_crew.py](src/dnd_mas_host/crews/narrator_crew/narrator_crew.py)) - **Flow-based**
   - Uses 3 specialized agents with explicit Flow routing:
     - **Prompt Validator**: Validates player prompts for conflicts, invalid actions, or ambiguities
     - **Action Extractor**: Parses prompts into structured action data (type, target, method, intent)
     - **Narrative Generator**: Creates engaging narratives from action results and game events
   - Architecture: `NarratorFlow(Flow[NarratorState])` with `@start()`, `@listen()`, `@router()` decorators
   - Tasks: `validate_prompt`, `action_extract`, `narrative_task`
   - All agents have `allow_delegation=False`

3. **Judge Flow** ([judge_crew.py](src/dnd_mas_host/crews/judge_crew/judge_crew.py)) - **Flow-based**
   - Uses 3 specialized agents with explicit Flow routing:
     - **Feasibility Agent**: Validates action legality under D&D 5E rules (action economy, components, resources)
     - **Difficulty Agent**: Assigns Difficulty Class (DC) from -1 to 21 based on context
     - **Consequence Agent**: Evaluates mechanical effects (HP, conditions, position, resources)
   - Architecture: `JudgeFlow(Flow[JudgeState])` with `@start()`, `@listen()`, `@router()` decorators
   - Tasks: `check_feasibility`, `assign_difficulty`, `evaluate_consequence`
   - All agents have `allow_delegation=False`

4. **NPC Agents** ([npc_crew.py](src/dnd_mas_host/crews/npc_crew/npc_crew.py))
   - **NPC Agent - Character**: Generates reactions based on NPC profile (personality, status, background)
   - **NPC Agent - Environment**: Generates environmental reactions (traps, collapse, alarms)
   - **NPC Agent - Storyline**: Generates storyline impacts, estimates in-game time passage

Each Flow/crew has:
- `<crew_name>_crew.py`: Flow or Crew definition with agent and task methods
- `config/agents.yaml`: Agent role, goal, and backstory definitions
- `config/tasks.yaml`: Task descriptions, tool usage guidance, and expected outputs

### State Management Architecture

**HostState (Flow's Pydantic Model)** - Primary state container:
- **Workflow coordination**: prompts, validation results, actions, difficulty, effects, NPC reactions
- **Game state (MVP)**: current_stage, current_venue, character_hp, character_max_hp
- **Shared across all Flows** via HostFlow
- **Accessible in Flow methods** via `self.state`
- **Must be explicitly passed** to sub-flows as input parameters

**Game State Data Flow**:
1. HostFlow reads state from HostState
2. HostFlow passes relevant state to sub-flow via `kickoff(inputs={...})`
3. Sub-flow processes and returns structured output
4. HostFlow updates HostState based on sub-flow output
5. Repeat for next sub-flow invocation

### MongoDB Vector Search (RAG)
[src/dnd_mas_host/tools/mongodb_vector_tools.py](src/dnd_mas_host/tools/mongodb_vector_tools.py) implements RAG with local embeddings:

**Embedding Model**: `all-mpnet-base-v2` (768 dimensions) via SentenceTransformer

**Databases**:
- `campaign`: Custom game content (npcs, venues, stages, stories)
- `5e-database`: D&D 5E 2014 SRD data from [5e-bits/5e-database](https://github.com/5e-bits/5e-database)

**12 Available Tools** (all agents have access to all tools):

*Campaign Tools (4):*
- `NPCVectorSearchTool`: Search NPCs (name, description, personality, intentions)
- `VenueVectorSearchTool`: Search venues (name, description, connections, actions)
- `StageVectorSearchTool`: Search story stages (name, description, venues)
- `UniversalVectorSearchTool`: Search all campaign collections

*D&D 5E Tools (7):*
- `MonsterVectorSearchTool`: Search creatures (stats, abilities, type)
- `SpellVectorSearchTool`: Search spells (level, components, effects)
- `RuleVectorSearchTool`: Search D&D 5E rules
- `EquipmentVectorSearchTool`: Search weapons, armor, gear
- `ClassVectorSearchTool`: Search class features
- `ConditionVectorSearchTool`: Search status effects
- `MagicItemVectorSearchTool`: Search magic items

*Game State Tool (1):*
- `GameStateSearchTool`: Query structured game state (HP, inventory, spell slots, conditions, venue, stage)

**Tool Integration**:
- Tools instantiated in Flow `_create_tools()` methods
- All 11 vector search tools passed to agents via `tools=self.tools` in `_load_agent_config()`
- `GameStateSearchTool` injected dynamically in HostFlow methods (requires HostState)
- Tool usage guidance provided in YAML task descriptions

**MongoDB Connection**: `mongodb://127.0.0.1:27017/` (local, runs on Docker Desktop)

## Key Technical Details

### Game Loop Use Case
The main interaction flow:

1. **Interface Agent** receives user prompt → passes to Narrator Flow
2. **Narrator Flow** validates prompt, extracts action → requests difficulty from Judge Flow
3. **Judge Flow** evaluates difficulty based on D&D rules → returns to Interface Agent
4. **Interface Agent** displays difficulty, awaits user confirmation → performs difficulty check (random roll)
5. **Judge Flow** evaluates consequences based on roll result → informs Narrator and NPC Agents
6. **NPC Agents** evaluate reactions → request difficulty checks from Judge
7. **NPC Agents** perform difficulty checks → return results to Judge
8. **Judge Flow** evaluates NPC action consequences → informs Narrator Flow
9. **Narrator Flow** generates narratives (user action + NPC reactions) → updates game state → passes to Interface
10. **Interface Agent** displays narratives and progresses story

**Exceptions**:
- Invalid/ambiguous prompts → Narrator requests clarification
- Actions too easy/impossible → Judge skips difficulty check, proceeds to effects
- Multiple NPC reactions → Ordered execution based on NPC priority

### HostState Fields (Pydantic Model)
`HostState` tracks workflow coordination via state-based control:
- Workflow: `workflow_step` (int), `current_agent` (str)
- User interaction: `prompt_text` (str), `prompt_valid` (bool), `validation_message` (Optional[str])
- Action processing: `action_extracted` (Dict), `Action_difficulty` (Dict[str, int]), `difficulty_check` (int), `skip_difficulty_check` (bool), `effect` (Optional[str])
- NPC reactions: `npc_reactions_completed` (List[Dict])
- Output: `final_output` (str)
- Game state (MVP): `current_stage` (str), `current_venue` (str), `character_hp` (int), `character_max_hp` (int)

### Tool Assignment Matrix

| Agent | Primary Tools | Use Cases |
|-------|---------------|-----------|
| **Judge: Feasibility** | RuleVectorSearchTool, SpellVectorSearchTool, ClassVectorSearchTool, GameStateSearchTool | Validate action legality: rules, spell components, class features, resource availability |
| **Judge: Difficulty** | MonsterVectorSearchTool, RuleVectorSearchTool, VenueVectorSearchTool, GameStateSearchTool, ConditionVectorSearchTool | Assign DC: enemy stats, environmental modifiers, player status, official guidelines |
| **Judge: Consequence** | MonsterVectorSearchTool, SpellVectorSearchTool, ConditionVectorSearchTool, GameStateSearchTool, RuleVectorSearchTool | Determine effects: damage, HP changes, conditions, resource expenditure |
| **Narrator: Prompt Validator** | VenueVectorSearchTool, NPCVectorSearchTool, StageVectorSearchTool, GameStateSearchTool | Validate prompt: current venue, NPCs present, game state, story alignment |
| **Narrator: Action Extractor** | VenueVectorSearchTool, NPCVectorSearchTool, GameStateSearchTool | Extract action with context: location, targets, player status |
| **Narrator: Narrative Generator** | NPCVectorSearchTool, VenueVectorSearchTool, StageVectorSearchTool, MonsterVectorSearchTool, SpellVectorSearchTool | Generate narrative: NPC descriptions, venue atmosphere, story context, spell/combat details |

**Note**: All agents receive ALL 12 tools - the matrix shows expected usage patterns, not restrictions. Tool selection is agent-driven based on task requirements.

## Important Notes

- This is a **Flow** project (not a traditional Crew project) - check `pyproject.toml`: `type = "flow"`
- Agents are configured via **hybrid approach**: Tools in Python (`_create_tools()`), other config in YAML
- **V2 Architecture**: Message-passing with Blackboard pattern (entry point: `python -m dnd_mas_host.interface`)
- **Legacy Architecture**: Flow-based with HostFlow orchestration (entry point: `python -m dnd_mas_host.interface.interface_agent`)
- All game state MUST be tracked in HostState/BlackboardManager (agents have no internal memory)
- If any unclear or question, please ask before proceed with the implementation or planning
